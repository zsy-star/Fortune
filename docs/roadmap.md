# 后续路线图

本文给出 Fortune 商用测试版 / 内部试用版后续工作的推荐顺序。原则：先确认规则和数据结构，再开放会写数据库或影响账务的功能。

## P0：保持文档和代码状态一致

- 持续同步 README、商用测试范围、功能状态总览。
- 每次开放或关闭入口后，更新对应文档和验收清单。
- 保持 `data/fortune.db` 不进入 Git。

## P1：复杂玩法规则文档与收口

- 持续补充已支持玩法的规则说明，并优先确认仍未开放的胆拖、组选、全包等玩法。
- 明确每种玩法：
  - 输入格式。
  - 保存格式。
  - 是否展开为号码。
  - 开奖号码参与范围。
  - 命中 / 未中 / 不支持判定口径。
  - 金额拆分口径。
- 规则未确认前，不接入正式结算。

## P2：结算金额和账务边界确认

- 已支持玩法继续补齐赔率配置匹配验收和旧快照兼容测试。
- 所有不支持或异常情况必须显示明确原因，不能默认按中奖处理。
- 余额、返水、佣金、完整账务盈亏进入下一阶段前，先确认账务模型和审计策略。

## P3：调单记录审计口径完善

- 当前特码调单 / 连肖调单已保存调单快照记录，后续只完善审计口径和验收脚本。
- 明确调整对象：
  - 特码号码。
  - 连肖组合。
  - 调整金额。
  - 调整前后快照。
  - 操作人和操作时间。
- 调单保存必须写操作日志。
- 未完成权限和审计前，不开放清空、重置、覆盖原始订单等高风险动作。

## P4：订单导入收口

- 当前已支持 txt/csv/xlsx 预览、模板下载、申报人、渠道、历史重复检测和确认导入成功行。
- 后续完善导入失败回滚验收、错误报告样式和更多真实样例覆盖。

## P5：权限系统设计

- 明确角色和权限：
  - 普通录单。
  - 查询 / 导出。
  - 开奖维护。
  - 结算确认。
  - 调单调整。
  - 高风险清空 / 恢复。
- 权限系统完成前，不开放清空订单、清空日志、批量删除等入口。

## P6：余额和账务设计

- 在复杂玩法和权限规则稳定后，再设计：
  - 返水参与计算。
  - 盈亏金额。
  - 客户余额。
  - 余额流水。
- 账务相关功能必须具备完整测试和审计日志。

## P7：打包发布检查

- 运行 Alembic 空库升级测试。
- 运行全量 pytest。
- 执行打包前只读自检：

```bash
python scripts/pre_release_check.py --project-root .
```

- 执行测试版构建 dry-run：

```bash
python scripts/build_test_release.py --project-root . --dry-run
```

- 本机试运行 PyInstaller 包。
- 复核 `data/fortune.db`、临时文件、测试文件不会进入发布包。
