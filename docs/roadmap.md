# 后续路线图

本文给出 Fortune 后续工作的推荐顺序。原则：先确认规则和数据结构，再开放会写数据库或影响账务的功能。

## P0：保持文档和代码状态一致

- 持续同步 README、商用测试范围、功能状态总览。
- 每次开放或关闭入口后，更新对应文档和验收清单。
- 保持 `data/fortune.db` 不进入 Git。

## P1：复杂玩法规则文档

- 补充连肖、多生肖、连尾、胆拖、组选、全包等玩法规则说明。
- 明确每种玩法：
  - 输入格式。
  - 保存格式。
  - 是否展开为号码。
  - 开奖号码参与范围。
  - 命中 / 未中 / 不支持判定口径。
  - 金额拆分口径。
- 规则未确认前，不接入正式结算。

## P2：连肖 / 多生肖 / 连尾等玩法结算规则确认

- 在规则文档确认后，补充 settlement engine 测试。
- 先实现结算预览，再开放正式结算。
- 所有不支持或异常情况必须显示明确原因，不能默认按中奖处理。

## P3：调单调整记录表设计

- 设计调单调整记录模型和迁移。
- 明确调整对象：
  - 特码号码。
  - 连肖组合。
  - 调整金额。
  - 调整前后快照。
  - 操作人和操作时间。
- 调单保存必须写操作日志。
- 未完成权限和审计前，不开放清空、重置、覆盖原始订单等高风险动作。

## P4：订单导入设计

- 明确导入文件格式、字段映射、校验规则和错误报告。
- 设计导入预览，不直接写入。
- 支持导入失败回滚。
- 导入成功写操作日志，并触发订单、日志、统计页面自动刷新。

## P5：权限系统设计

- 明确角色和权限：
  - 普通录单。
  - 查询 / 导出。
  - 开奖维护。
  - 结算确认。
  - 调单调整。
  - 高风险清空 / 恢复。
- 权限系统完成前，不开放清空订单、清空日志、批量删除等入口。

## P6：赔付、余额和账务设计

- 在复杂玩法和权限规则稳定后，再设计：
  - 赔率/返水参与计算。
  - 赔付金额。
  - 盈亏金额。
  - 客户余额。
  - 余额流水。
- 账务相关功能必须具备完整测试和审计日志。

## P7：打包发布检查

- 运行 Alembic 空库升级测试。
- 运行全量 pytest。
- 执行打包前只读自检：

```bash
python scripts/pre_release_check.py --project-root .
```

- 执行测试版构建 dry-run：

```bash
python scripts/build_test_release.py --project-root . --dry-run
```

- 本机试运行 PyInstaller 包。
- 复核 `data/fortune.db`、临时文件、测试文件不会进入发布包。
